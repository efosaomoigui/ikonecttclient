# Settlement, wallet funding and service authorization — API 1.2.0

21 October 2026. This clarification supersedes conflicting Stage5A funding/activation assumptions. **Payment settlement funds the wallet. Customer authorization initiates renewal. Service activation is a separate confirmed outcome.**

## Shared contract

The HTTP inventory stays **78 paths / 95 operations**, with the same six roles and permissions. `WalletEntry.kind` adds `SETTLEMENT_CREDIT`; `settlementPaymentId` is an optional nullable UUID linking the credit to its registered funding payment. Amounts, balances and dates remain backend-authoritative NGN minor units. Synchronize strict canonical enum snapshots; never silently drop a settlement credit because it is not a manual top-up. `actorId:null` is a system settlement posting. The entry has its own immutable `WTX-…` reference, a unique `settlement:<paymentId>` operation key and the registered merchant reference in its description. Source identifiers are references, not service-activation instructions.

Capabilities include `paymentSettlement:'not-connected'`. No public provider callback or provider checkout route is enabled. No live provider, merchant account, signature protocol, settlement-fee policy or credentials have been approved. A generic adapter contract and disabled implementation are shipped; test-only authenticated protocol fixtures are not a real provider integration.

## Settlement processing boundary

1. Trusted future checkout code uses the approved provider to create a payment for the authenticated customer, then registers its exact provider/account/payment identity, merchant reference, expected amount, currency and customer-scoped UUID with `SettlementService.register`. This is an internal boundary, not a user-supplied callback or public registration API. Registration creates no credit and has no order/subscription effect.
2. A future approved transport/worker calls `SettlementService.ingest(rawEnvelope)`. It must preserve the exact raw bytes and headers. The configured adapter authenticates them using the provider's approved protocol, validates replay/timestamp/merchant environment requirements, and independently retrieves authoritative settlement status using server credentials. Callback claims alone are never proof. The core validates the adapter result and its binding to the registered payment/customer, provider account, amount and NGN currency.
3. INITIATED, PENDING and FAILED authenticated events are recorded as IGNORED, without credit. Invalid/unverified/lookup-failed events throw before any financial write. Only SETTLED with a settlement reference and date can post funds. A generic successful payment/capture/acknowledgement is not automatically a settled amount.
4. One serializable transaction locks the registered payment and wallet, inserts an immutable verified event receipt, marks the payment CREDITED, inserts one SETTLEMENT_CREDIT and updates the ledger-maintained wallet projection. Deferred database constraints require the matching event, payment and credit to commit together. The transaction does not write orders, subscriptions, renewal operations or provisioning jobs.
5. Same-event/same-content replay returns the recorded result. Changed content under one provider/account/event ID conflicts. A different event for an already credited payment is recorded as DUPLICATE without another credit. Later pending/failure events do not retract settled credit. Provider chargebacks/refunds need an approved separate policy, not a fabricated failure or ordinary credit reversal.

Receipts retain identifiers, status, digest and timestamps, not raw callback bodies, secrets, bank evidence or signatures. Payment terms and receipts are immutable. Customer wallet projection is transactional and remains backed by the one in-house ledger, not an unrelated settlement balance.

The future transport must acknowledge only after durable processing succeeds. Database/lookup/amount/binding conflicts and capacity failures are unacknowledged and must enter the approved provider retry/alert/reconciliation flow; no successful acknowledgement or wallet credit is fabricated. A previously recorded non-final event remains its original receipt on replay. An actual later settlement must arrive as a new authenticated event, or through an approved server-reconciliation event protocol. No retry scheduler or public webhook is claimed while the provider is unconnected.

`SettlementService.reconcile(customerId)` uses a consistent read snapshot to compare projection totals against signed ledger sums and every registered settlement's unique ledger allocation. It reports discrepancies; it never repairs financial history by editing balances. Database transaction rollback/retry is safe because no provider request is repeated inside a financial transaction.

## Allocation and existing order payments

Existing confirmed `Payment` rows remain consumed ORDER allocations and retain their order status, receipts and audit trail. There is no historical backfill, provider conversion, or bridge that credits a legacy order payment. Registration claims both merchant reference and provider payment reference in the same global normalized registry used by historical order payments/manual wallet reports. A consumed reference cannot be reused for funding; cross-provider raw-reference collisions conservatively conflict for reconciliation rather than creating another credit.

Future provider payments always settle to WALLET first, including a payment started in an order-related customer journey. The order context must not mean a second direct-order credit or automatically mark an order paid. This boundary deliberately accepts no `orderId` allocation field. After funding, an explicit separately authorized purchase/reservation must consume available wallet funds and link its ledger debit to the legitimate service transaction. Stage5A implements that operation for eligible existing-service renewals. A future wallet-funded NEW_CONNECTION/PLAN_CHANGE purchase requires its own approved authorization, pricing, hold and confirmed-fulfilment extension before being enabled. Such order checkout is not silently enabled here.

The existing manually reported ORDER payment workflow remains for compatibility, explicitly separate from the new provider wallet-first channel; its verification does not itself invoke provisioning. Its funds are already allocated to the order and never appear as unspent wallet funds. Manual WALLET reports still require Finance verification. This does **not** impose manual approval on authenticated automatic provider settlement, which credits directly through its separate boundary.

## Customer and Admin display

Display wallet balance/history independently of subscription status. All four combinations are valid: zero/positive wallet × active/inactive service. Funding must not refresh a service into Active, infer expiry or call a renewal/provisioning endpoint. A positive balance with an expired or suspended service remains a valid funded, inactive service.

The customer deliberately selects Renew Plan, reviews the authoritative quote, explicitly confirms, and only then sends the existing UUID/priceVersion request. The backend rechecks ownership, policy, price, service/coverage/provider eligibility, conflicts and funds before reserving. A separate authorized processing action initiates renewal. Capture and authoritative service update occur only on matching confirmed outcome; definite failure releases and uncertainty retains a reviewable hold. No recurring renewal, expiry-triggered debit, funding-triggered reservation or automatic activation exists.

Portal: show SETTLEMENT_CREDIT as settled wallet funding, distinct from pending manual reports and service debits; source reference may be displayed but no fabricated settlement-details endpoint. Admin: show the same immutable entry and source ID; system actor is expected. Existing manual correction/reversal UI applies only to the approved credit kinds; do not offer provider-settlement reversal/chargeback as an arbitrary adjustment. Finance/Support read access and backend permissions are unchanged. No additional operator approval is required between an approved verified settlement and its wallet credit.

## Unconnected provider dependencies

Before enabling an approved adapter/transport, supply the provider and merchant/environment identity, exact signature/raw-body and replay protocol, server verification API/credentials, authoritative settled-versus-paid semantics, gross/net/fees/partial-settlement policy, reference mapping, webhook delivery/retry requirements, polling/reconciliation event identity, chargeback/refund rules and operational alert ownership. This implementation supports exact full NGN settlement matching the registered expected amount; it does not invent fees, partial credit or another currency. Do not turn the existing payment simulator into a real settlement provider.
