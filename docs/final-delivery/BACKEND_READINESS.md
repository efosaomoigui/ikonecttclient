# Ikonectt backend readiness — 10 November 2026

The application-owned workflows can be verified against an isolated PostgreSQL database. Production integration is pending: the client wallet transport, authoritative account and service data, and live notification delivery have not been configured or exercised. No production environment was deployed.

| Workflow | Current implementation | Launch dependency or limitation |
| --- | --- | --- |
| Enquiries and customer onboarding | The API records leads. Authorized staff create customers and issue expiring, single-use activation credentials. Public signup is absent. Onboarding, reissue and profile edits are audited. | Confirm the approved account identifier and CRM ownership. Production requires a staff-supplied identifier and does not generate a simulated one. Connect the public site to the approved lead submission path before promising delivery. |
| Identity and profile | Staff/customer sign-in, role permissions, scoped customer data, reset, password change, logout, session expiry and revocation. Passwords are scrypt-hashed; reset and session tokens are hashed at rest. Session issuance checks the current credential and account state inside its transaction. | Confirm existing identity system ownership and approved delivery channel for activation/recovery. Reassess distributed rate limits before scaling beyond one API instance. |
| Plans and coverage | Published catalogue and staff-maintained, address-level eligibility with verification evidence. Unknown eligibility is explicit. | Confirm authoritative catalogue, service and coverage sources. Local catalogue and coverage records are not evidence of live client integration. |
| Orders and billing | Customer requests are scoped. Manual order-payment reporting, Finance verification and receipts are separate from provisioning. Payment amount and reference checks guard allocation. | Approve the manual payment instructions and verification workflow or supply the authoritative payment contract. No live gateway or webhook is enabled. |
| Provisioning | Separate authorized request and outcome; acknowledgement does not activate a service. Stage/test fixtures can exercise success, failure and timeout. | Confirm service identity, authorized operator process, provisioning API and authoritative outcomes before using an automated integration. |
| Wallet and renewal | The isolated local ledger supports tested top-ups, holds, explicit renewal, capture, release and reconciliation. Client authority mode disables local wallet and settlement operations. Its balance adapter requires a mapped account and a validated authoritative response. The unconfigured adapter returns unavailable, without returning zero or falling back to the local ledger. | Production requires `WALLET_AUTHORITY=client`. The client must supply wallet mappings, balances/history contracts, and authorized renewal and outcome semantics. History, top-up and renewal remain unavailable in client mode pending those contracts. The local ledger is not imported or merged into the client wallet. |
| Support | Customer submission creates a persisted ticket with a stable UUID, initial conversation and audit record. Staff can assign enabled Support/Admin users, reply and change status; customers can see their own status and conversation. Closed tickets reject further messages. Reply, resolution and closure can queue notifications. | Confirm local ownership or external helpdesk synchronization. Long conversations return the latest 500 messages; full-history pagination is not implemented. |
| Notifications | Durable encrypted outbox, leased dispatch, bounded retries and explicit delivery state. Ticket terminal-status notifications are queued only when status changes. | Confirm delivery provider, sender, templates, worker deployment and delivery monitoring. Simulated success is never production delivery. |
| AI-assisted support | Public site uses scripted guidance; the API guidance route is deterministic, bounded and rate limited. It points users to authenticated support or account routes and has no account lookup, write capability or AI credentials. | AI is optional. Confirm approved knowledge, privacy/retention, provider and escalation rules before enabling a model. A future provider should use an approved knowledge source, authorized account reads, and customer-confirmed ticket submission through the existing ticket service. No AI wallet, payment, renewal or provisioning writes. |

## Rollout requirements

- Use a clean environment and database provisioned for the target deployment. Never promote development fixture rows or credentials. Run additive migrations against an isolated rehearsal copy first, verify backup and restore, and preserve reference mappings and audit records.
- Set `NODE_ENV=production`, `WALLET_AUTHORITY=client`, exact HTTPS origins, the target database URL and a protected notification encryption key. Production rejects simulated adapters and excludes Swagger. Protect the runtime and outbox worker separately, with least-privilege credentials and health/error monitoring.
- Verify the real onboarding and recovery notification path, coverage source, service readback and authorized outcome before launch. Verify that missing client mappings and provider outages show an honest unavailable state rather than presenting local or fabricated data.

## Verification

- The dedicated local PostgreSQL service was restored on `127.0.0.1:55438` using its existing test data directory. `prisma migrate deploy` against `ikonectt_test` found all four migrations applied; none were pending. No test reset or production connection was needed.
- Backend type checking, production compilation and canonical API parity were checked. The contract remains version 1.2.0, with 78 paths and 95 operations.
- The complete backend suite passed: 79 tests, zero failures or skips. The focused wallet suite independently passed all 22 tests.
- Automated workflow coverage includes account setup/recovery, session revocation, role and ownership isolation, Support assignment/replies/closure, encrypted outbox, manual order payments and provisioning, and financial invariants in the isolated local ledger. Tests verify that client authority with no configured transport exposes neither local balances nor local transaction history.
